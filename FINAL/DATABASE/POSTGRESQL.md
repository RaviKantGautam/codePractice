Here is a comprehensive list of 50 mid-to-senior level SQL and PostgreSQL interview questions, structured into core technical domains. The answers focus on architecture, performance trade-offs, and internal mechanics expected of a backend engineer with 5 to 6 years of experience.

## 1. Query Optimization & Performance Tuning

### Q1: How do you analyze a slow query in PostgreSQL?

Use `EXPLAIN (ANALYZE, BUFFERS) your_query;`. `ANALYZE` executes the query to show real vs. estimated row counts, while `BUFFERS` shows shared memory block hits, reads, and writes. Look for Sequential Scans on large tables, high-cost disk spills, or massive row estimation mismatches.

### Q2: What is the difference between `EXPLAIN` and `EXPLAIN ANALYZE`?

`EXPLAIN` shows the execution plan generated by the query planner based on database statistics without running the query. `EXPLAIN ANALYZE` actually executes the query, providing real execution times and exact row counts alongside the estimates.

### Q3: How does the query planner use statistics, and how do you update them?

The planner uses statistics stored in `pg_statistic` (exposed via `pg_stats`) to estimate row counts and choose paths (e.g., Index vs. Seq Scan). Statistics are updated automatically by the `autovacuum` daemon or manually by running `ANALYZE table_name;`.

### Q4: When does a B-Tree index scan switch to a Bitmap Index Scan?

When a query matches too many rows for a standard Index Scan but too few for a Sequential Scan. PostgreSQL scans the index, builds a bitmap of matching pages in memory, sorts the pages by physical disk location, and then fetches the data sequentially to minimize random disk I/O.

### Q5: What are the performance issues with `OFFSET` pagination, and what is the alternative?

`OFFSET N` forces the database to scan and discard the first $N$ rows before returning data, leading to $O(N)$ performance degradation on high page numbers. The alternative is **Keyset Pagination (Seek Method)**, using a `WHERE id > last_seen_id ORDER BY id LIMIT X`, which utilizes an index to jump straight to the correct row.

### Q6: How do you optimize a query with a massive `IN` clause containing thousands of constants?

A massive `IN` list forces the planner to parse a large expression tree. Optimize it by passing the values as an array using `ANY(?::int[])`, or loading them into a temporary table/CTE and performing an `INNER JOIN`.

### Q7: What is the risk of using `SELECT *` in high-throughput backend services?

It wastes network bandwidth and memory by fetching unused columns (especially large text or binary data via TOAST). It also prevents the query planner from using efficient **Covering Indexes** (Index-Only Scans) and risks breaking application code if the schema changes.

### Q8: What causes a "Row Estimation Mismatch" in a query plan, and why is it dangerous?

It happens due to stale statistics, complex correlated predicates, or skewed data distribution. It is dangerous because it can cause the planner to select highly inefficient join strategies, like picking a Nested Loop instead of a Hash Join.

### Q9: What is a correlated subquery, and how do you optimize it?

A correlated subquery references columns from the outer query, forcing it to evaluate once for every candidate row. Optimize it by rewriting it into a flat `LEFT JOIN` or a non-correlated subquery with a window function.

### Q10: How does `work_mem` affect query performance?

`work_mem` specifies the amount of memory allocated for internal sort operations and hash tables before writing to temporary disk files. If a query's sort or join phase exceeds `work_mem`, it spills to disk, degrading performance significantly.

## 2. Indexing Deep Dive

### Q11: Explain the difference between B-Tree, GIN, and GiST indexes.

* **B-Tree:** Default for sorting and equality comparisons (`<`, `<=`, `=`, `>=`, `>`).
* **GIN (Generalized Inverted Index):** Ideal for composite items where you search for element components (e.g., Arrays, JSONB keys/values, Full-Text Search).
* **GiST (Generalized Search Tree):** Used for geometric data, network addresses, and range types where data overlaps or has spatial coordinates.

### Q12: What is a Partial Index, and when should you use it?

A partial index is built over a subset of a table defined by a conditional expression (`WHERE clause`). Use it to index highly queried, small subsets of data (e.g., indexing only active orders: `WHERE status = 'active'`), saving storage and memory.

### Q13: What is an Expression (Functional) Index? Provide a use case.

An index computed over the result of a function applied to columns, rather than the column values themselves.

```sql
CREATE INDEX idx_users_lower_email ON users (LOWER(email));

```

Use case: Ensuring fast lookups when executing case-insensitive lookups.

### Q14: What are Covering Indexes, and what is the purpose of the `INCLUDE` clause?

A covering index includes extra payload columns directly in the index leaf nodes using the `INCLUDE` clause. This allows the query planner to perform an **Index-Only Scan**, retrieving data directly from the index without fetching the actual table row from disk.

### Q15: How do multi-column (composite) B-Tree indexes work regarding column order?

PostgreSQL multi-column indexes strictly follow the left-most prefix rule. An index on `(A, B)` can optimize queries filtering by `A` or `A AND B`, but cannot optimize queries filtering *only* by `B` unless a loose index scan applies.

### Q16: What is index bloat, and how do you fix it without locking readers and writers?

Index bloat occurs when deleted or updated rows leave empty spaces in the index structures that aren't reclaimed. Fix it concurrently without blocking active operations using:

```sql
REINDEX INDEX CONCURRENTLY index_name;

```

### Q17: Can PostgreSQL use multiple indexes simultaneously for a single table in a query?

Yes. Through a **Bitmap Index Scan**, PostgreSQL can scan two distinct indexes (e.g., one on `user_id` and one on `status`), generate bitmaps of matching row locations, perform a bitwise `AND`/`OR` in memory, and then fetch the rows.

### Q18: What are BRIN indexes, and when are they highly efficient?

**BRIN (Block Range Indexes)** store the minimum and maximum values of data blocks rather than individual rows. They are highly efficient for massive, multi-gigabyte tables where data is naturally ordered by a column over time (e.g., `created_at` or auto-incrementing IDs), requiring a fraction of B-Tree storage.

### Q19: How do you index a JSONB column for efficient key-value lookups?

Use a GIN index. You can apply the default `jsonb_ops` operator class (supports top-level key/value searches) or `jsonb_path_ops` (smaller index size, supports deep path queries but fewer operators).

### Q20: Why might the query planner perform a Sequential Scan even if an index exists?

1. The table is very small (disk layout makes a sequential scan cheaper than index + heap lookups).
2. The query filters for data that constitutes a large percentage of the table (high selectivity threshold exceeded).
3. A function is applied to the column in the `WHERE` clause without a matching expression index.

## 3. Concurrency, Locking & MVCC

### Q21: How does MVCC (Multi-Version Concurrency Control) work in PostgreSQL?

When data is updated or deleted, PostgreSQL does not overwrite the existing row. Instead, an `UPDATE` marks the old row version (tuple) as invisible to future transactions and writes a completely new tuple. Each row contains hidden system metadata columns (`xmin` and `xmax`) to determine visibility based on the current transaction’s isolation snapshot.

### Q22: What is the difference between standard `VACUUM` and `VACUUM FULL`?

* **Standard VACUUM:** Removes dead tuples and marks the space as reusable for future inserts within that table. It runs concurrently without locking the table.
* **VACUUM FULL:** Recreates the entire table on disk to reclaim all space and return it to the OS. It requires an exclusive lock (`ACCESS EXCLUSIVE`), blocking all reads and writes.

### Q23: Explain the isolation levels supported by PostgreSQL.

* **Read Committed (Default):** A statement sees only data committed before the statement began.
* **Repeatable Read:** A statement sees only data committed before the *transaction* began. Prevents non-repeatable and phantom reads.
* **Serializable:** Provides full transaction isolation. If a concurrent write conflict could cause an anomaly, the transaction fails with a serialization error and must be retried.

### Q24: What is the Write-Ahead Log (WAL), and why is it critical?

WAL is an append-only log where changes are written and flushed to persistent disk *before* they are applied to the actual database pages (Write-Ahead logging). This ensures ACID durability: if the server crashes, PostgreSQL can replay the WAL to restore the database to a consistent state.

### Q25: What is the difference between `ROW EXCLUSIVE` and `ACCESS EXCLUSIVE` locks?

* **ROW EXCLUSIVE:** Acquired automatically by data modification commands (`UPDATE`, `DELETE`, `INSERT`). It blocks structural alterations but allows concurrent reads/writes on other rows.
* **ACCESS EXCLUSIVE:** Acquired by commands like `ALTER TABLE`, `DROP TABLE`, or `VACUUM FULL`. It conflicts with all lock modes, completely blocking any concurrent access to the table.

### Q26: How do you detect and resolve deadlocks in PostgreSQL?

PostgreSQL automatically detects deadlocks using its internal deadlock detector after a threshold specified by `deadlock_timeout` (default 1s) and aborts one of the conflicting transactions. To prevent them, ensure your application code updates multiple rows or tables in the exact same sequential order across all transactions.

### Q27: What is the difference between `SELECT ... FOR UPDATE`, `NOWAIT`, and `SKIP LOCKED`?

* `FOR UPDATE`: Locks selected rows for updates, forcing other transactions trying to modify or lock those rows to wait.
* `NOWAIT`: Errs immediately if a row lock cannot be acquired right away.
* `SKIP LOCKED`: Skips any locked rows and returns unlocked rows instantly. This is ideal for building high-concurrency background worker queues.

### Q28: What is a serialization failure (`SQLSTATE 40001`), and how must the application handle it?

It occurs in `REPEATABLE READ` or `SERIALIZABLE` isolation levels when PostgreSQL detects a concurrent write conflict that violates data isolation consistency. The application must catch this exception and retry the entire transaction from the beginning.

### Q29: What is a Hot Update (Heap-Only Tuples - HOT) in PostgreSQL?

If an updated row does not change any indexed columns and the data page contains enough free space, PostgreSQL places the new row version on the exact same page. This avoids creating new pointers in the index, drastically reducing index bloat and saving I/O overhead.

### Q30: How can you check for long-running transactions that might be blocking VACUUM?

Query the `pg_stat_activity` view to find transactions in an `idle in transaction` state:

```sql
SELECT pid, age(clock_timestamp(), query_start), query 
FROM pg_stat_activity 
WHERE state = 'idle in transaction' 
ORDER BY 2 DESC;

```

## 4. Database Architecture & Storage

### Q31: Why is external connection pooling (like PgBouncer) critical for PostgreSQL at scale?

PostgreSQL allocates a dedicated backend process for every client connection via a `fork()` call, which consumes significant memory (~10MB+ per connection) and CPU tracking locks/snapshots. A pooler like PgBouncer allows thousands of application clients to share a much smaller pool of actual database connections, preventing resource exhaustion.

### Q32: Explain the three types of declarative Table Partitioning.

* **Range:** Partitions tables based on a continuous range of values (e.g., partitioning log tables by month or year).
* **List:** Partitions tables by explicitly listing explicit keys (e.g., partitioning users by `country_code`).
* **Hash:** Partitions tables by applying a modulus and remainder to a routing hash key, evenly distributing rows across a fixed number of partitions.

### Q33: What is the difference between Physical Replication and Logical Replication?

* **Physical Replication:** Copies byte-for-byte disk blocks from the primary server to the replica via WAL. The replica must be an identical copy of the primary database.
* **Logical Replication:** Streams structural data changes (Inserts/Updates/Deletes) based on replication identities. This allows cross-version replication, filtering rows/columns, or streaming changes to different databases.

### Q34: What is TOAST (The Oversized-Attribute Storage Technique)?

PostgreSQL database pages have a fixed size of 8KB. When a row contains columns that exceed a threshold (typically 2KB), PostgreSQL automatically compresses the large attributes and moves them out of the main table row into a separate system storage area called the TOAST table.

### Q35: What are the risks of using UUIDv4 as a primary key, and how can you mitigate them?

UUIDv4 values are completely random. When used as a B-Tree primary key, they cause random index insertions, which leads to heavy index page fragmentation, cache thrashing, and performance degradation once the index exceeds memory sizes. Mitigation includes using ordered UUID variants like **UUIDv7** or sequencing patterns.

### Q36: How do you tune `shared_buffers` and `max_connections` for production?

* `shared_buffers`: Controls the dedicated memory PostgreSQL uses for caching data blocks. It is typically set to **25% of total system RAM** on production servers.
* `max_connections`: Keep it minimal (e.g., 100-500) to avoid backend process thrashing, relying on an external connection pooler to multiplex traffic.

### Q37: What is a Checkpoint in PostgreSQL, and how does it affect write I/O?

A checkpoint is a periodic event where PostgreSQL flushes all dirty (modified) data pages cached in shared buffers out to the physical disk, marking the WAL position safe for recovery. Aggressive checkpoints cause write spikes; tuning `max_wal_size` and `checkpoint_completion_target` helps smooth out this I/O load.

### Q38: What is a Replication Slot, and what happens if a replica goes down with an active slot?

A replication slot ensures that the primary server preserves the necessary WAL segments required by a replica, preventing the replica from falling out of sync. If the replica goes down permanently, the primary will retain WAL files indefinitely, filling up disk storage until the primary runs out of space.

### Q39: What is Transaction ID (XID) Wraparound, and how does PostgreSQL prevent it?

PostgreSQL uses a 32-bit unsigned integer for transaction IDs, capping total concurrent trackable transactions at ~4 billion. `autovacuum` prevents wraparound by routinely freezing old transaction IDs, turning them into a permanent historical state so the counter can safely wrap back around to zero.

### Q40: What is the difference between `pg_dump` and a physical basebackup (`pg_basebackup`)?

* `pg_dump` extracts a logical text/archive backup containing SQL commands to recreate the schema and data. It can be restored selectively or across database versions.
* `pg_basebackup` takes a raw physical copy of the database cluster’s file directory, making it faster to restore for point-in-time recovery (PITR) but restrictive to identical database versions.

## 5. Advanced SQL & PostgreSQL Features

### Q41: What is the difference between `UNION` and `UNION ALL`?

`UNION` eliminates duplicate rows across its result sets by executing an implicit sort and deduplication step, which incurs memory and CPU costs. `UNION ALL` merges the datasets exactly as they are without deduplication, making it significantly faster.

### Q42: Differentiate between `RANK()`, `DENSE_RANK()`, and `ROW_NUMBER()`.

* `ROW_NUMBER()`: Assigns a strict sequential integer to every row (e.g., 1, 2, 3, 4).
* `RANK()`: Assigns identical numbers to duplicate values, but skips subsequent values (e.g., 1, 2, 2, 4).
* `DENSE_RANK()`: Assigns identical numbers to duplicate values without skipping any subsequent integers (e.g., 1, 2, 2, 3).

### Q43: When does PostgreSQL materialize a Common Table Expression (CTE)?

Since PostgreSQL 12, standard side-effect-free CTEs are automatically inlined (`NOT MATERIALIZED`) if they are referenced only once later in the query. You can force materialization using the explicit `MATERIALIZED` keyword to create an isolated optimization boundary when needed.

### Q44: How do you handle an UPSERT statement safely?

Use the `ON CONFLICT` clause combined with a unique constraint or index identifier:

```sql
INSERT INTO users (email, status) VALUES ('test@example.com', 'active')
ON CONFLICT (email) 
DO UPDATE SET status = EXCLUDED.status;

```

The `EXCLUDED` table represents the row value that was originally rejected due to the conflict.

### Q45: What is the difference between `text`, `varchar(N)`, and `char(N)` in PostgreSQL?

Under the hood, `text` and `varchar` use the identical variable-length internal storage layout. `varchar(N)` adds an extra runtime length check overhead. `char(N)` applies blank padding spaces up to length $N$, wasting storage space. Use `text` or `varchar` without modifiers by default.

### Q46: How do you execute Dynamic SQL safely inside a PL/pgSQL function?

Use the `EXECUTE` command combined with the `USING` parameter clause to bind variables cleanly. Never concatenate user strings directly to prevent SQL injection vulnerabilities:

```sql
EXECUTE 'SELECT * FROM users WHERE id = $1' INTO user_record USING user_id;

```

### Q47: How do you refresh a Materialized View without blocking concurrent read operations?

Create a unique index on the materialized view first, then refresh it using the `CONCURRENTLY` keyword:

```sql
REFRESH MATERIALIZED VIEW CONCURRENTLY my_view;

```

This applies changes smoothly by building a temporary version and applying a delta instead of dropping and recreating the view.

### Q48: How do you implement hierarchical/tree structures efficiently using SQL?

Use a recursive Common Table Expression (`WITH RECURSIVE`). The query initializes an anchor member query, then runs a recursive term query that references the anchor execution step iteratively to traverse down parent-child foreign key relationships.

### Q49: What is the difference between `NULLS FIRST` and `NULLS LAST` in an `ORDER BY` clause?

By default, `ASC` sorting puts null values last, while `DESC` sorting puts null values first. Specifying `NULLS FIRST` or `NULLS LAST` forces uniform behavior. For optimal performance, ensure your matching index matches the exact null configuration of your query's sort clause.

### Q50: How can you listen for real-time asynchronous notifications from PostgreSQL?

Use the built-in pub/sub infrastructure via `LISTEN channel_name;` and `NOTIFY channel_name, 'payload';`. Applications maintain a persistent database connection to catch events asynchronously without continuously polling tables.

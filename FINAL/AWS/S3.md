# Amazon S3 — Interview Questions (1–3 years)

Interview questions and answers for a backend and cloud software engineer with 1–3 years of experience.

---

## Fundamentals

#### 1. What is Amazon S3, and what is it not?

**Answer:** S3 is object storage. You store an object (the bytes plus metadata) under a key in a bucket. It is not a filesystem: there are no partial-file locks, no directories (prefixes are just key names), and you do not mount it as a POSIX disk for a database. Use it for uploads, images, logs, backups, static sites, and data-lake files. Use EBS or EFS when a program needs a real disk.

---

#### 2. What are buckets, keys, prefixes, and objects?

**Answer:** A **bucket** is a container with a globally unique name in a region you choose. A **key** is the object name, such as `invoices/2026/03/a.pdf`. A **prefix** is the part before a slash and is only a naming convention. An **object** is the data, a content type, and metadata, up to 5 TB using multipart upload. The bucket does not contain real folders.

---

#### 3. What consistency model does S3 provide?

**Answer:** S3 provides **strong read-after-write consistency** for PUT and DELETE of objects. After a successful upload, a following read returns the new object. After a successful delete, a following read does not return it. You do not need to design for the old eventual-consistency behavior of overwrites. Listing very large prefixes is still a paginated API, not an instant directory snapshot.

---

#### 4. How does a backend upload a file from a user’s browser without proxying the bytes?

**Answer:** Issue a **presigned URL** (or a presigned POST) with the SDK. The URL includes a signature and an expiry. The browser uploads directly to S3. Your server never holds the file. Restrict the key prefix, content length, and content type in the signature, and keep the expiry short (minutes, not days).

---

#### 5. What is a presigned URL, and what does it not do?

**Answer:** It grants temporary access to one operation (GET or PUT) using the credentials that signed it. Anyone with the URL can use it until it expires. It does not replace a bucket policy for long-term access, and it does not encrypt the object by itself. If the signing credentials lack permission, the URL fails even if it looks valid.

---

#### 6. When would you choose S3 instead of EBS or EFS?

**Answer:** Choose S3 when many clients need the same durable object, when you want lifecycle policies and very low storage cost, or when the access pattern is PUT/GET of whole objects. Choose EBS for a single instance’s disk. Choose EFS when many instances need a shared POSIX filesystem (uploads processed by several workers, a home directory). S3 is the default for blobs.

---

## Storage classes and lifecycle

#### 7. What are the storage classes a backend engineer should be able to name?

**Answer:**

* **S3 Standard:** frequent access, millisecond GET.
* **Standard-IA and One Zone-IA:** infrequent access, retrieval fee, One Zone keeps a single AZ.
* **Intelligent-Tiering:** automatic movement between frequent and infrequent tiers when you do not know the pattern.
* **Glacier Instant Retrieval, Flexible Retrieval, and Deep Archive:** archives. Instant still has millisecond access with a higher storage discount. Flexible and Deep Archive take minutes to hours to restore.
* **S3 Express One Zone:** very high request rates in one AZ, for latency-sensitive object access.

Lifecycle rules move or expire objects. You do not manually recopy them.

---

#### 8. What does a lifecycle rule typically do for application logs?

**Answer:** Transition logs from Standard to Standard-IA or Glacier after 30 or 90 days, then **expire** (delete) them when the retention period ends. Abort incomplete multipart uploads after a few days so orphaned parts do not bill forever. Filter on a prefix such as `logs/`. Versioned buckets also need a rule for **noncurrent versions**, or old versions never go away.

---

#### 9. What is versioning, and what happens on delete when it is on?

**Answer:** Versioning keeps every overwrite as a new version id. A DELETE without a version id adds a **delete marker**. The object looks gone, but older versions remain and you still pay for them. A delete of a specific version id actually removes that version. Suspend versioning to stop creating new versions. It does not purge old ones.

---

#### 10. What is replication, and when do you use it?

**Answer:** **Same-Region Replication** or **Cross-Region Replication** copies new objects to another bucket. Use CRR for disaster recovery and for placing data near another region’s compute. Replication is not retroactive unless you ask to replicate existing objects. Delete markers and versioning need to be considered explicitly. Replication is asynchronous, so it is not a substitute for a strong read of the source bucket.

---

#### 11. What is a multipart upload, and when is it required?

**Answer:** You upload parts in parallel and complete them with a manifest. It is required above 5 GB and recommended for anything large enough to fail midway (often 100 MB and up). If you never call Complete or Abort, parts remain and you pay for them. Set a lifecycle rule to abort incomplete multipart uploads.

---

## Security and access

#### 12. How do IAM policies and bucket policies differ?

**Answer:** An **IAM policy** is attached to a user or role and says what that identity can do. A **bucket policy** is attached to the bucket and can allow or deny principals, including other accounts and public access. Both must allow the call. An explicit **Deny** on either side wins. Prefer roles for applications and a bucket policy for cross-account access.

---

#### 13. What is Block Public Access?

**Answer:** Four account- and bucket-level switches that block public ACLs and public bucket policies. Leave them on unless the bucket is a deliberate public website or public download host. A bucket can still be private and serve users through presigned URLs or through CloudFront with an origin access control.

---

#### 14. How should a private bucket be served to the internet?

**Answer:** Put **CloudFront** in front, with **origin access control** so only CloudFront can read the bucket. Users hit the CDN. The bucket stays blocked from public access. This gives you TLS, caching, and a place to attach WAF. Do not open `s3:GetObject` to `Principal: *` for a normal app bucket.

---

#### 15. What encryption options do you choose?

**Answer:** **SSE-S3** (AWS-owned keys) is the simple default and is on for new objects. **SSE-KMS** uses a KMS key so you can audit decrypts in CloudTrail and limit which roles can read. **SSE-C** means you send the key with each request. You rarely want that. Bucket keys with SSE-KMS cut KMS request costs when many objects are read.

---

#### 16. What is a pre-signed upload’s main security mistake?

**Answer:** Signing a URL that allows any key, any content type, and a long expiry. A leaked URL can then fill the bucket or overwrite objects. Constrain the key prefix, set a content-length range, use a short expiry, and do not sign with an admin role. Server-side encryption and a bucket policy that denies unencrypted uploads close the other gap.

---

## Application patterns

#### 17. How do you handle a file larger than the API Gateway or Lambda payload limit?

**Answer:** Do not send the file through API Gateway or Lambda. Return a presigned PUT URL, let the client upload to S3, and trigger processing from an **S3 event** (or EventBridge) to a Lambda, SQS queue, or ECS worker. The API only accepts metadata and the object key.

---

#### 18. What is the claim-check pattern?

**Answer:** A queue message stays small and contains an S3 key, not the payload. The producer uploads the blob to S3, then sends the key on SQS or SNS. The consumer reads the object. Use it when the payload would exceed SQS (1 MiB) or SNS (256 KB), or when the same blob is read by several consumers. Delete or lifecycle the object after processing.

---

#### 19. How do S3 event notifications work, and what can they miss?

**Answer:** A bucket can notify SQS, SNS, Lambda, or EventBridge on create and delete events. Notifications are usually fast but are not a database transaction: your upload can succeed and the message can fail independently, so consumers must be idempotent. Enable EventBridge delivery if you want filtering rules without wiring every prefix in the bucket notification UI. Versioning adds version ids you should log.

---

#### 20. Why might a high request rate on one prefix throttle?

**Answer:** S3 partitions by prefix. A single hot key or a tiny set of keys (a counter object everyone updates, or all writes under one second-level prefix) can return **503 Slow Down**. Spread keys (include a hash or id early in the key). S3 scales prefixes automatically over time, but a single object is still one object. Do not use S3 as a lock or a counter.

---

#### 21. How do you read part of a large object without downloading it?

**Answer:** Send a **Range** header on `GetObject`. Clients that support multipart GETs can parallelize. S3 Select can push simple filtering into S3 for some formats, but most backends just download the object or a byte range. For analytics over many files, Athena or a data tool is a better fit than `GetObject` in a loop.

---

#### 22. What are S3 bucket keys you should not use as a database index?

**Answer:** Listing a prefix is a paginated LIST call, not a query planner. It gets expensive and slow as a substitute for “find invoices by customer”. Store the lookup in DynamoDB or RDS (customer id to S3 key) and use S3 only for the bytes. LIST is for maintenance and batch jobs.

---

## Failure, cost, and scenarios

#### 23. A `PutObject` succeeds and the next `GetObject` from another service returns 404. What do you check?

**Answer:** Strong consistency means this is usually not a delay. Check the bucket name, region, key (leading slashes and case), and whether the reader is in another account without permission (access denied is sometimes confused with missing objects in app code). A delete marker from versioning also makes a plain GET look like 404. Log the version id and the exact key.

---

#### 24. How do you stop a bucket from being deleted with production data in it?

**Answer:** Enable **MFA delete** only if you truly need it (it is easy to lock yourself out). More commonly: versioning, a bucket policy that denies `s3:DeleteBucket` and denies deletes except for a break-glass role, Block Public Access, and replication to a second bucket that the application role cannot delete. Lifecycle expiration is the controlled way to remove data.

---

#### 25. What is the difference between 403 and 404 for a private object?

**Answer:** S3 often returns **403** for a missing key when the caller is not allowed to know whether the object exists (`s3:ListBucket` is absent). A real missing object with list permission returns **404**. When debugging a presigned URL, a 403 is usually a bad signature, wrong region, expired URL, or a policy deny, not a typo in the key. Check CloudTrail data events if they are enabled.

---

#### 26. How would you back up a bucket you cannot afford to lose?

**Answer:** Versioning plus replication to another region and another account is the usual design. The replica account’s write path is locked down so a bug or a compromised app role in the source cannot wipe both. S3 is already redundant inside a region across AZs (except One Zone classes). Cross-region replication is for regional loss and for account compromise, not because a single PUT is fragile.

---

#### 27. Users upload CSV files that a worker must process once. How do you wire it?

**Answer:** Presigned PUT into a prefix `incoming/`. An S3 event sends a message to SQS (not straight to a single Lambda if you want buffering). A worker gets the key, processes the file, writes results, and moves the object to `processed/` or writes a status row in DynamoDB. A DLQ catches poison files. Idempotency is keyed by the object key and version id, because S3 can deliver a notification more than once.

---

#### 28. How do you calculate whether Standard-IA is cheaper than Standard?

**Answer:** Standard-IA has a lower storage price, a higher per-GET price, and a minimum storage duration (typically 30 days). Objects you read often, or small objects you overwrite weekly, can cost more on IA. Lifecycle into IA only prefixes you actually read rarely. Intelligent-Tiering has a small monitoring fee and is the safer choice when the pattern is unknown.

---

#### 29. What must a bucket policy allow for a CloudFront origin, and what must it deny?

**Answer:** Allow `s3:GetObject` only from the CloudFront service principal, restricted with a condition on the source ARN of that distribution (origin access control). Deny public principals. Do not also leave a public ACL. Writes from your backend use an IAM role, not the CloudFront allow.

---

#### 30. What would you monitor and alarm on for an application bucket?

**Answer:** 4xx and 5xx from the application’s S3 client metrics or CloudWatch request metrics (enable them on the bucket), a spike in `5xx`, bucket size if cost matters, and failed multipart uploads. If the bucket is a pipeline, alarm on the age of the oldest object in `incoming/` or on the SQS queue fed by events. CloudTrail data events are noisy and cost money. Enable them on sensitive buckets, not blindly on every log bucket.
